# Высокий мир −15000…15000 (вариант В)

Цель: мир по высоте от −15000 до 15000 без швов — строить, ходить, видеть блоки на любой высоте. Как у модов
«кубических чанков» (Cubic Chunks, Better Cubic Chunks), но дешевле: протокол чанков остаётся ванильным (столбцы),
снимаем только то, что реально мешает высоте. Нужен наш мод (ядро Hoka Odyssey) — ванильный клиент в такой мир не
зайдёт.

Высоты кратны 16, поэтому фактически: **−15008 … 15007** (1876 секций по 16 блоков).

## Что мешает (проверено 24.11.2026)

1. **Упаковка координаты блока в 64 бита.** Клиент 1.21.11: X и Z по 26 бит, Y — 12 бит (−2048…2047). Отсюда
   ванильный предел высоты: `DimensionType.Y_SIZE = 2^12 − 32 = 4064`, −2032…2031. Всё выводится из одного числа
   при загрузке класса `BlockPos` (`ldc 30000000` в `<clinit>`), а не зашито константами → меняется ОДНОЙ вставкой:
   X/Z 24 бита (±8 388 607 по горизонтали), Y 16 бит → лимит высоты становится ±32 752.
2. **Minestom** упаковывает позицию в сети так же (26/26/12, зашито в `NetworkBufferTypeImpl$BlockPositionType`) и
   не даёт создать измерение выше −2032…2031 (проверка в `DimensionType.Builder`). Оба места — заменить у себя.
3. **Память и трафик столбца высотой 1876 секций** (замер Minestom, 24.11):
   - сервер, без света: **396 КБ на столбец** (441 столбец = 171 МБ) — Minestom держит объект на каждую секцию,
     даже пустую;
   - пакет чанка: **16.5 КБ** без сжатия (пустые секции дёшевы) — нормально;
   - **свет Minestom (`LightingChunk`): 2.4 с на один столбец** — так нельзя, нужен свой свет только около непустых
     секций (небо над ними клиент и так считает полным).
   - клиент: игра тоже создаёт объект на каждую секцию + объект отрисовки на каждую секцию в дальности прорисовки
     (у Sodium — так же). Оценка ~0.5–1 ГБ при дальности 16 — НЕ замерено, этап 1.
4. **Сохранение мира.** Anvil хранит номер секции байтом (−128…127 секций = ±2048 блоков) → свой формат хранения.

## Важные последствия

- **Мод нужен всем.** Сервер шлёт тип измерения выше ванильного → ванильный клиент (и наш мод старее нужной версии)
  не войдёт: отключится на входе. Старым версиям мода автообновление не успеет прийти (оно после входа) → один раз
  поставить новое ядро вручную. Включаем высокий мир флагом в конфиге, когда все обновились.
- **Мод на других серверах.** Внутреннюю упаковку меняем глобально (это безопасно), а СЕТЕВУЮ — только на нашем
  сервере: сервер ещё на этапе входа (configuration) шлёт моду «высокий мир», и мод переключает сетевой формат позиций.
  На других серверах — ванильный формат. Цена: на других серверах дальше ±8.4 млн блоков по горизонтали — нельзя
  (там почти никто не бывает).
- **Sodium, Lithium и прочие моды** должны пережить новую упаковку: они берут её из полей `BlockPos` (не константы) —
  должно работать, но проверить на сборке игрока (этап 1).

## Статус (24.11.2026)

Сделано и выкачено (ядро мода 0.28.1, server.jar):
- упаковка координат 24/24/16, сетевой формат по сигналу сервера, высокое измерение hoka:tall, карта `tall`, `/hotall [y]`;
- свет (TallChunk): небо вертикальными лучами + растекание вбок внутри секции, свет блоков внутри секции; пустые секции
  не шлются (выше верхней — клиент считает небо полным; Sodium для секций без данных берёт 15); при смене блока свет
  столбца рассылается раз за тик; 28 мс на столбец вместо 2.4 с у LightingChunk;
- своё хранение (TallLoader): файл на столбец в maps/<карта>/tall/, только непустые секции + блоки с данными
  (проверено: столбец с площадками и сундуком = 333 байта, всё восстанавливается);
- граница мира ±8 000 000;
- Sodium: отрисовочные секции только в окне ±(дальность+1) по высоте от камеры (SodiumTallMixin) — было >50% кадра;
- «сторож кадров» (FrameWatch, лог `[фриз]`): после правки Sodium фризы от высокого мира не найдены; оставшиеся —
  Dynamic FPS (System.gc при смене фокуса окна) и разовые при входе.

Осталось: ванильная отрисовка без Sodium (ViewArea держит объект на КАЖДУЮ из 1876 секций в дальности — у игрока без
Sodium будет очень много памяти), общая пустая секция в клиенте, генерация по зонам высоты, корабли/гравитация по высоте.

## Этапы

**Этап 1 — прототип «высокая карта» (проверить, что вообще живёт)**
- Ядро 0.27: упаковка 24/24/16; сетевой формат по сигналу сервера; сигнал в configuration.
- Сервер: своя `BlockPositionType` (по флагу), высокое измерение в обход проверки билдера, тестовая карта
  `tall`: земля на 0, площадки на ±12000, без света от Minestom.
- Проверка у игрока: вход, полёт/телепорт на 12000 и −12000, ставить/ломать блоки там, F3 (память, FPS), с Sodium.

**Этап 2 — клиент выдерживает высоту**
- Общая пустая секция вместо тысяч пустых объектов (копия при первой записи).
- Вертикальная дальность прорисовки: секции дальше ±N по высоте от камеры не заводятся в отрисовку (ваниль ViewArea
  и Sodium RenderSectionManager). Настройка «вертикальная дальность».
- Небо и свет: секции без данных над поверхностью — полный свет неба (так клиент уже умеет).

**Этап 3 — сервер выдерживает высоту**
- Пустые секции без объектов (Minestom: общая пустая секция).
- Свой расчёт света: только непустые секции и их соседи; в пакете — только они.
- Своё хранение мира (вместо Anvil): разреженные секции по столбцам.
- Генерация по зонам высоты (недра / поверхность / атмосфера / космос) — под планеты и станции.

**Этап 4 — игра**
- Корабли, гравитация корабля, вакуум и зоны гравитации «космоса» — по высоте (космос выше атмосферы и т.п.).
- Граница мира по горизонтали ±8 млн.
- Понятное сообщение старым клиентам вместо обрыва соединения (если получится — на этапе входа).

**Этап 5 — совместимость**: сборка игрока (Fabulously Optimized: Sodium, Lithium, ImmediatelyFast, EntityCulling,
MoreCulling…), Iris, клиенты 26.x через ViaVersion — решить: поддерживаем ли.
